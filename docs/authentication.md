# Muse Provider Authentication Setup

This guide explains how to set up authentication for the Omnigent Muse harness. The harness delegates authentication to Muse, which supports multiple providers with different authentication requirements.

## Supported Providers

The Muse harness supports three providers, each with distinct authentication characteristics:

### Meta Provider

The **`meta`** provider routes model calls to Meta's Model API. It requires authentication credentials.

**Setup steps:**

1. **Install Muse**: Ensure you have the Muse CLI installed.
   ```sh
   curl -fsSL https://dev.meta.ai/install.sh | bash
   ```

2. **Authenticate** using one of these approaches (in order of precedence):
   
   a. **Using `muse login` (interactive device-code flow):**
   ```sh
   muse login
   ```
   Follow the prompts to authenticate in your browser. Credentials are stored securely in Muse's auth store (`~/.config/muse/auth.json`).

   b. **Using `muse auth set` (token-based):**
   ```sh
   muse auth set meta <your-meta-api-key>
   ```
   This stores the token in the Muse auth store.

   c. **Using the `META_API_KEY` environment variable (harness environment):**
   ```sh
   export META_API_KEY=<your-meta-api-key>
   ```
   Set this in the environment where the Omnigent harness runs. This takes precedence over stored credentials and is useful for CI/CD environments.

3. **Precedence order**: Muse checks credentials in this order:
   - `META_API_KEY` environment variable (if set in the harness process)
   - Stored credential from `muse auth set` or `muse login`
   - Fall back to default provider if neither is available

**Security note:** Never pass credentials as command-line arguments or hardcode them in agent specifications. Use environment variables or Muse's built-in credential storage instead.

### Echo Provider

The **`echo`** provider is credential-free and designed for testing the MSP transport layer without connecting to any model API. It echoes back mock responses.

**Use cases:**
- Verifying the MSP connection between the harness and Muse
- Transport smoke tests to confirm the integration is wired correctly
- Development and testing workflows

**Setup:** No authentication required. Simply declare `provider: echo` in your agent spec or set the environment variable:
```sh
export HARNESS_MUSE_PROVIDER=echo
```

**Example verification:**
```yaml
executor:
  type: omnigent
  harness: muse
  model: echo
  config:
    provider: echo
```

### Local Provider

The **`local`** provider routes model calls to a local model instance available on your machine. Authentication requirements depend on your local setup.

**Setup:** Configure your local model provider according to Muse's `local` provider documentation, then declare it in your agent spec:
```yaml
executor:
  type: omnigent
  config:
    provider: local
```

**Note:** Specific authentication steps for the `local` provider depend on your local model configuration. Refer to the Muse documentation for details on configuring local model endpoints.

## Provider Configuration

### Via Agent Specification

Declare the provider in your Omnigent agent YAML:

```yaml
executor:
  type: omnigent
  harness: muse
  model: muse-large           # or appropriate model for your provider
  config:
    provider: meta            # or echo, local
```

### Via Environment Variables

Override spec-declared values with environment variables (takes precedence):

```sh
export HARNESS_MUSE_PROVIDER=meta
```

The `HARNESS_MUSE_PROVIDER` environment variable accepts: `meta`, `echo`, or `local`.

### Default Behavior

If `provider` is omitted in both the spec and environment:
- The harness uses Muse's configured default provider
- Muse's default is typically `meta`

## Verification Workflow

Before running a full Omnigent workload, verify that your provider and authentication are correctly configured. These commands check provider readiness without starting a model turn:

### 1. Verify Muse is installed and on PATH

```sh
muse --version
```

Expected output: version information (e.g., `muse 1.4.0`).

### 2. Check authentication for the meta provider

```sh
muse session list
```

This lists existing Muse sessions. If authentication fails, you'll see an error message indicating missing credentials. If it succeeds, you have valid authentication.

Alternatively, check that credentials are stored:

```sh
cat ~/.config/muse/auth.json
```

You should see a JSON structure with a `providers` section containing a `meta` entry with your stored credential. **Do not edit this file directly** — use `muse auth set` or `muse login` to manage credentials.

### 3. Test echo provider (credential-free)

Set the provider and attempt to start a session:

```sh
export HARNESS_MUSE_PROVIDER=echo
muse --provider echo serve --session-id test-session
```

Press Ctrl+C to stop the server after confirming it starts successfully. The `echo` provider should initialize immediately without authentication errors.

### 4. Verify the harness can load the Muse plugin

```sh
python -c "from omnigent.harness_plugins import valid_harnesses; assert 'muse' in valid_harnesses(); print('Muse harness discovered')"
```

## Troubleshooting Authentication Failures

### `authRequired` Error After Successful MSP Connection

The most common authentication issue is `authRequired` arriving as a **terminal turn failure** after the MSP connection initializes successfully. This can be misleading because:

1. The MSP connection (stdio-based) initializes correctly
2. The first turn starts without apparent transport errors
3. The error surfaces only after Muse attempts to call the model API

This is **not a transport problem** — it indicates the selected provider cannot authenticate. Verify your setup using the **verification workflow** above.

### Common Auth Failures and Solutions

**"Muse provider authentication failed (provider=meta, authRequired)"**

- **Solution for meta provider**: Run one of:
  ```sh
  muse login
  ```
  or
  ```sh
  muse auth set meta <your-meta-api-key>
  ```
  or set the environment variable in the harness:
  ```sh
  export META_API_KEY=<your-meta-api-key>
  ```

**"Muse provider authentication failed (provider=unknown, authRequired)"**

- **Cause**: The provider could not be determined (e.g., Muse's config is corrupted or no provider is configured).
- **Solution**: Verify that `~/.config/muse/settings.json` exists and is valid JSON. Check Muse's configuration documentation.

**Authentication works locally but fails in CI/CD**

- **Cause**: The `META_API_KEY` environment variable is not set in the CI/CD environment, and Muse's credential store (local to your machine) is not available in the CI/CD container/runner.
- **Solution**: Set `META_API_KEY` in your CI/CD environment variables:
  ```sh
  export META_API_KEY=${{ secrets.META_API_KEY }}  # GitHub Actions example
  ```

**Provider mismatch error**

- **Cause**: The provider configured in the agent spec differs from the active provider in Muse.
- **Example**: Spec declares `provider: echo` but Muse is configured for `provider: meta`.
- **Solution**: Ensure the spec's `provider` value matches your Muse configuration, or let the spec omit `provider` to use Muse's default.

### Debug Trace

Enable detailed tracing of provider requests and responses:

```sh
export MUSE_TRANSPORT_TRACE=1
```

This prints raw provider request and response lines to stderr (with credentials scrubbed for security). Use this to diagnose unexpected provider behavior.

## Security Best Practices

1. **Never embed credentials in YAML specs**: Always use environment variables or Muse's credential storage.
2. **Use `META_API_KEY` only in trusted environments**: The environment variable is visible to the harness process and should only be used in secure, automated deployments.
3. **Rotate credentials regularly**: If you suspect your `META_API_KEY` was compromised, contact Meta security and regenerate the key.
4. **Scrub logs**: Muse automatically redacts credentials from logs, but verify that your logging pipeline does not capture `META_API_KEY` environment variable values.

## Next Steps

Once you have verified your provider authentication:

1. Declare the provider in your Omnigent agent spec
2. Start your Omnigent workload
3. Monitor the first turn for authentication errors (which surface as terminal events, not transport errors)
4. If `authRequired` appears, revisit the **troubleshooting** section above

For more information on Muse and its providers, visit the [Muse Code documentation](https://meta-models.github.io/muse-code-sdk/).
